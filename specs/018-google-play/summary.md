# Summary: Google Play Billing, core without the Play Billing library (spec 018, C10)

**Date**: 2026-10-07 · **Status**: core implemented, host QA and live-backend contract QA green, device E2E and the gated phases deferred, committed on branch `018-google-play` (8b34925) · **Backend contract**: `saveme-backend@1a0e1cd` (spec 024, `google-play.yaml` v1.15). **No Play Billing dependency was added**; until the gated G1 phase lands, the shipped Android build reports Google Play as unavailable.

## What was built

- **`PlayBillingClient` port** (connect, product details, launch purchase flow, query purchases, observe updates) with **no acknowledge or consume member**. Android and iOS bind `UnavailablePlayBillingClient`; the dev flavour binds `SwitchingPlayBillingClient(real, scripted)` through Dev tools → "Google Play (scripted)" (a scripted client for host tests, dev and E2E).
- **`BillingApi`** gained `playAccountReference`, `verifyPlayPurchase` and `restorePlayPurchases` (plain strings across the data layer, P-10.6). New `ApiErrorCode` entries `PURCHASE_ALREADY_LINKED` and `PURCHASE_NOT_VERIFIED` with English and Arabic copy.
- **Idempotency key** `gp1:` + SHA-256 of (user, purchase state, token), computed by an expect/actual `sha256` (`MessageDigest` on Android, CommonCrypto on iOS, no dependency): stable across retries and process death, changing when a pending purchase becomes purchased and hourly when rechecking after a 202. The app's keys equal, byte for byte, the keys the server accepted and replayed.
- **`PlayPurchaseVerifier`** runs on sign-in, app start, foreground (at most once a minute), Plan screen open or refresh, and each purchase update; it sends only purchases Google reports as not acknowledged. 503, 429 and "request in progress" retry with the same key, at most 6 sends per purchase per run; 409 `PURCHASE_ALREADY_LINKED` and 422 are not retried. **The app never acknowledges, consumes or grants a plan itself** (a 202 means pending: wait for the server).
- **`PlayRestoreService`**: silent after a real sign-in (not a cold start) and only when Google Play reports purchases; a tap sends everything (25 per request, most recent first, one combined result message).
- **Plan screen**: "Restore purchases", "Enter code", and the allowed links "Manage in Google Play" and "Fix payment" (grace, and hold when a verify answer reported it) that start no payment; notes for pending, hold, paused, grace, test purchase and another-account purchase (held in memory only, cleared at sign-out by `PlayBillingCleaner`, which resolves the verifier lazily to avoid a Koin cycle). Prices come only from Play `ProductDetails` (micro-units to exact integer minor units), so **none are shown until G1**; the catalogue price is no longer shown (FR-037).
- `PlayStoreLinks`, `PlayPrices`, `BillingAnswerApplier`, coordinator wiring and Koin. No Room change (Google Play's purchase list is the record). `AppConfig.inAppSubscribe = false` in every flavour; no Subscribe button exists.
- **E2E assets (written, not run)**: Maestro flows in `.maestro/018-google-play/` (US1-background-verify, US1-pending-then-purchased, US2-restore-tap, US2-restore-nothing, US3-another-account, US4-grace-fix-payment, US5-prices), `common/play-open-devtools.yaml`, `play-script-purchase.yaml`, `play-back-to-home.yaml`, `api.js` `playVerify` and `playAccountReference`, a `+play-subscription` seed in `run-e2e.sh` with a `# e2e-play-script: {...}` header (the script file is written inside the backend container; `@REFERENCE@` is replaced by the fresh account's account reference).

## Results

- **Host QA** (`qa-report.md`): every acceptance scenario, FR, SC and edge case maps to a passing test or a code path; 0 open gaps (five found and closed; the US6/FR-041–049 Subscribe items are listed as GATED). 4,073 host tests, 0 failures, 0 skipped (the four-task gate with `--rerun-tasks`, run twice, and `cleanAllTests build allTests --continue --no-build-cache`; the iOS simulator test task is skipped on Linux, the iOS test code compiles). `devDebugRuntimeClasspath` has no billingclient artifact and no Gradle or build file changed.
- **Live contract QA** (89 requests, 54 on `billing/google/*`; statuses 63×200, 2×202, 8×422, 4×409, 4×400, 3×401, 3×503, 2×429; 59 answers captured in `CapturedPlayResponses.kt` with made-up tokens and no credentials, replayed by `GooglePlayLiveReplayTest`, 27 tests): account reference is 64 hex, stable per account, different between accounts; verify 200 has the documented shape with `acknowledged:true` set by the server, replay with the same key gives the same answer with `Idempotency-Replayed`; a pending purchase gets 202 and the plan stays Free, once purchased a new key gives 200 and Plus; 409 for a first link and for a reference match; 422 `PURCHASE_NOT_VERIFIED` and 422 `VALIDATION_FAILED` at `/product_id`; missing or invalid key 400, reused key 409; verify limit 429 with `Retry-After` 3563; a disabled gateway 503 with `Retry-After` 3600; restore: empty list 200, a mixed list returns `linked`, `linked_elsewhere`, `not_verified` and `pending` in request order, a repeat gives `already_yours`, 25 items 200, 26 items or duplicate tokens 422 (the app never sends either), restore limit 429 after 10 an hour; after re-verifying one token `/me/subscription` shows grace as `grace` and canceled as `active` with `auto_renew:false`, while on_hold, paused, expired and revoked all show the Free plan with `provider:null`; a manual Plus · Yearly granted via `OperatorSubscriptions::grant` still governs over a Google Play monthly purchase. No backend bug found.
- **Run environment**: the dev driver is `disabled` and mapping `plus_monthly` needed a plan-price edit on the dev DB, which the permission system denied; QA used a throwaway `php -S` server inside the dev container with the `fake` gateway and env-var overrides, pointed at the test database (`saveme_backend_main_test`) with the billing seeder run there. The dev DB and the dev `.env` were never changed (`.env` sha256 identical before and after).
- **Fixes found live**: (1) **Retry-After clamp (client defect)**: `PlayPurchaseVerifier.retryLater` capped every wait, including the server's `Retry-After`, at 15 minutes, so the app would have resent against a limit (about an hour) that had not reset; the server's wait is now honoured up to 24 hours, and only the app's own 30-second doubling stops at 15 minutes. (2) **Wrong member name in the E2E seed**: `run-e2e.sh` and `.maestro/common/api.js` read `data.account_reference`; the real member is `data.obfuscated_account_id`. (3) Tests added for traceability: FR-003 (a layering scan that billing never touches the sync outbox), FR-004 (`UnavailablePlayBillingClientTest`), US5.3 (Arabic and English money format with Western digits), FR-023 and FR-053 (`PlanAccessibilityTest`: polite live regions, tags, 48 dp targets at 200 % font); a replay test's `toSortedMap` in common code (which iOS test compilation rejects) was replaced.
- Goldens: new `screen_plan_*` for restore_running, restore_result, restore_refused, restore_unavailable, play_grace, play_hold, play_paused, play_pending, play_another_account and play_manage_test (each in en, ar, en_fs2); existing Plan goldens (free, active_with_prices, grace, stale_unavailable, arabic_names) changed on purpose (the "Restore purchases" button was added and the catalogue price removed).
- Test hardening: `ReportsCapturedParityTest` (spec 014, test only) no longer closes the in-memory database in `tearDown` (a leftover background write leaked an uncaught exception into later coroutine tests); a race in the new `PlayTestEnv` (ConcurrentModificationException when reading recorded requests) fixed; `BillingLayeringTest` now checks only `PlayBillingClient` interface members for acknowledge or consume (it wrongly flagged the `acknowledged` data field).

## Assumed defaults

Owner away with delegated authority; each the conservative option.

### Design

1. **P-12 reconciliation**: rule 3 read literally ("MUST expose only 'restore purchases' and 'enter code'"; spec 005 FR-010 and SC-004 read it that way). The backend's "verify = single-item restore" (ADR-0026) covers which API calls the app may make; it adds no button. What ships: "Restore purchases" and "Enter code", plus links to Google Play's own subscription centre ("Manage in Google Play", "Fix payment") that start no payment. The in-app Subscribe flow is fully designed behind `AppConfig.inAppSubscribe = false`. No "Upgrade" link to the Play Store listing (that page does not sell an app's subscriptions). **Recommended amendment** (client v1.4.0, backend P-10.2 mirrored): "The in-app billing surface MUST expose only Google Play's own purchase sheet, 'restore purchases' and 'enter code'; links to Google Play's subscription centre are allowed." The owner should also confirm the two links are acceptable now; removing them is two buttons and their tests.
2. Recovery: Google Play's purchase list is the record; the app keeps no Room table or stored state.
3. Purchases are sent on sign-in, app start, foreground (at most once a minute), Plan screen open or refresh, and each purchase update; there is no connectivity trigger (the app has no connectivity signal).
4. Restore runs silently after a real sign-in and only when Google Play reports purchases; a tap sends everything with an empty list when there is nothing; one combined result message.
5. Background verifies are silent apart from a "You're on <plan>" snackbar if the Plan screen is open.
6. Purchases belonging to another account show a note with no Sign out button and are not resent during that run.
7. Notes (pending, hold or paused, test purchase) are held in memory only and cleared at sign-out.
8. Prices: Google Play's base-plan price converted from micro-units to exact integer minor units and formatted by the app; the catalogue's `amount_minor` is never shown.
9. Lifetime products are sent like any purchase, never offered for sale; upgrades, downgrades and offers are left to Google Play.
10. Dev and E2E use a scripted Google Play client in the dev flavour against the backend's `fake` gateway with the same tokens; Maestro never buys.

### Implementation

11. Hashing through platform APIs (no dependency); `PlayBillingCleaner` resolves the verifier lazily.
12. Cold start runs a verify pass, a real sign-in runs restore, the foreground floor is 60 s.
13. The server's `Retry-After` is honoured up to 24 hours (the idempotency window); the app's own backoff doubles from 30 s up to 15 minutes.
14. The catalogue file is `CapturedPlayResponses.kt` (tasks.md updated to match).
15. The Arabic strings are the spec's assumed defaults and need the owner's review (about 25 strings).

## Remaining risks

- Real Google Play is untested until G1; live QA used the scripted `fake` gateway, so acknowledgement failure, concurrent-request handling (`IDEMPOTENCY_REQUEST_IN_PROGRESS`), a per-item `unavailable` outcome, `acknowledged:false` and a real 426 are not reproduced live (covered by contract examples and host tests).
- **Backend gaps** (non-blocking): `MySubscription` shows hold and paused as the Free plan with `provider:null`, so those notes last only for the run that saw them in a verify answer; it has no `test` flag (the "Test purchase" label lasts only for that run); it names the plan, not the Play product (the app maps plan to product through the catalogue); it still has no id (carried over from spec 015), so "governing is the redeemed one" is inferred from provider, plan and period end; a 202 still carries `current_period_end`; the fake moves `current_period_end` on every read.
- Without G2, no new purchase can start in the app; purchases started in Google Play itself (resubscribe, a payment that completes later, process recovery) still reach the account.
- Merge hotspots with later phases: build files (G1 will touch them, as will the C16 Firebase phase — rebase one on the other).
- Spec 016's static Google Play notice could gain a "Manage in Google Play" link (not done, to avoid touching that branch).
- Pre-existing flakes noted: `ReportsPerformanceTest` has timing sensitivity under load, and graph tests can leak a Room exception under load.
